## 3. What to look at in each workflow

### PRQA 00 · Main Pipeline
```
Pipeline Input (Execute Workflow Trigger) ─┐
Manual Synthetic Test Trigger → Load Synthetic Fixture ─┴→ Normalize Pipeline Input
  → Load Policy & Registry (worker /config)
  → Policy Gate: Review-Only & Repository          (Code: route = synthetic | allowed | blocked)
  → Execution Allowed? (Switch, 3 outputs)
       synthetic (mock) ─┐
       allowed (live)  ──┴→ Stage 02 → Stage 03 → Stage 04 → Stage 05 → Stage 06 ┐
                                                                     → Stage 07 ┴→ Merge Reporting Results → Final Summary
       blocked ──────────→ Record Blocked Decision (worker /events) → Blocked: Review-Only / Repository Disabled (end)
  every Stage node has an error output → Stage Failed → Sanitize → Record Stage Error → Pipeline Failed (end)
```
- **Policy Gate** mirrors `worker/prqa_worker/policy.py`; the worker re-checks on `POST /jobs`, so this is the early, visible decision, not the only one.
- In review-only mode a real repository can only reach the **blocked** output (`REVIEW_ONLY_MODE`). The blocked branch now also calls `Notify Blocked Decision (worker → Discord)` so the requester sees a **BLOCKED** notice (mock sink in Phase 1) instead of silence; it is deduplicated per delivery id.
- `Final Summary` additionally exposes `entry_point`, `trigger_source`, `actions_run_url` and `result_validation`.
- Workflow setting *Error workflow* = PRQA 08.

### PRQA 01 · GitHub Webhook Receiver
```
GitHub Webhook (raw body) → Verify HMAC Signature (Code, crypto) → Signature Valid?
   ✗ → Respond 401 Invalid Signature
   ✓ → Validate Event & Extract PR → Eligible Event?
          ✗ → Respond 200 Ignored (ping / not pull_request / not labeled / not qa-test:* / draft / closed)
          ✓ → Claim Delivery ID (worker /deliveries/claim) → Dedupe by Delivery ID → Duplicate Delivery?
                 ✓ → Respond 200 Duplicate
                 ✗ → Respond 202 Accepted → Start Main Pipeline (async)
```
- `Validate Event & Extract PR` accepts the opt-in label `$env.PRQA_TRIGGER_LABEL` (default `to be test` → `$env.PRQA_DEFAULT_TEST_LEVEL`) as well as `qa-test:*`; `unlabeled` / `closed` / `synchronize` go to `Lifecycle Event?` → `Cancel Active Jobs (worker /jobs/cancel)` → `Respond 200 Lifecycle Handled` (see [LABEL_TRIGGER_FLOW.md](./LABEL_TRIGGER_FLOW.md)).
- HMAC is computed over the **raw** bytes with `GITHUB_WEBHOOK_SECRET` (`$env`).
- Dedupe layer 1 = worker delivery table (layer 2 = one active job per `repo#pr@sha:level` on `POST /jobs`).

GitHub Actions entry (same workflow, second webhook node):
```
GitHub Actions Webhook (POST /prqa/actions, raw body) → Prepare Actions Intake (Code: base64 body + X-PRQA-* headers, no secret)
   → Verify, Validate & Claim (worker /webhook/actions/intake) → Route Intake Outcome (Switch)
        accepted    → Build Pipeline Input (Actions) → Respond 202 Accepted (Actions) → Start Main Pipeline (async)   [shared node]
        duplicate   → Respond 200 Duplicate (Actions)
        unauthorized→ Respond 401 · forbidden → Respond 403 (repo not registered) · rejected → Respond 422 · rate_limited → Respond 429 · other → Respond 503
```
- The worker does all the security work (`worker/prqa_worker/actions_intake.py`): constant-time HMAC-SHA256 over `<timestamp>.<raw body>` with `PRQA_WEBHOOK_SECRET` (worker env only — n8n never sees it), ±300 s window, `schemas/actions-request.schema.json`, PR-URL/repository/number/SHA consistency, open/non-draft, registry membership, server-derived idempotency key `gha:<repo>#<pr>@<sha>:<level>` claimed in the delivery table (replay protection), per-repository + global + failed-auth rate limits.
- The 202 body carries a `policy_preview` so the Actions log can say up front that a real repository will be **blocked** while review-only.
- The intake HTTP node deliberately has **no retry**: a retried intake could turn an accepted request into a "duplicate" without a pipeline start.

### PRQA 02 · PR Context Collector
`Resolve GitHub API Endpoint` reads `endpoints.github_api_base` from the policy (mock in review-only) → `Fetch PR Metadata` → `Fetch Changed Files` → `Fetch Unified Diff` → `Assemble Raw PR Data` → `Sanitize & Build Context Package (worker)` → `Attach Context`. Redaction/truncation/`changed_operations` extraction happen in `worker/prqa_worker/validation.py::build_context`.

### PRQA 03 · Prompt Builder (LLM)
`Build LLM Request from Reference Template (worker)` → `Provider Key Present? (or mock)` (checks the proxy prompt credential and a plain-http proxy base) (false → `Provider Key Missing → Reference Fallback`, nothing sent) → `Call Prompt LLM via Model Proxy (budgeted chat/completions)` (error output → `LLM Unavailable → Reference Fallback`) → `Extract Generated Prompt` → `Validate Prompt / Fallback to Reference (worker)` → `Prompt Source?` → `Prompt: LLM-generated ✓` / `Prompt: Reference fallback` → `Attach Prompt`.
- Templates (v2): `prompts/llm/system.v2.md` (authoritative instructions: evidence tags, no reference carry-over, 11-section structure, Required/Regression/Conditional/Blocked labels, self-review), `prompts/llm/user.v2.md`; canonical reference: `prompts/reference/Senior_QA_Reference_Prompt.md` (byte-identical to `examples/`, used for structure only); result contract appended: `prompts/opencode/result-contract.v1.md`.
- Quality gate (`prompt_builder.py::validate_generated_prompt`): the 11 headings, labels and `curl`/`$BASE_URL`/`$TOKEN`/`BLOCKED` present, no secrets, no injected phrases, length bounds, **plus** deterministic lints against the PR context — evidence-aware (v2.1): endpoint/method, query-parameter, identifier, numeric-limit and status-code claims on `[FACT: diff|openapi]` lines and inside Required/Regression scenarios must be literally present in the trusted evidence (diff, OpenAPI operations, file paths, title — never the PR description); reference-specific terms, speculative families (concurrency/tenant/performance) presented as Required/Regression, database claims without SQL, duplicate/out-of-order/empty sections and exact duplicate scenarios are rejected; Conditional/Blocked or verify-marked claims, unevidenced expected status codes and near-duplicates only warn. Any error → deterministic, evidence-tagged reference fallback (same 11 sections). Description-only inputs: the deterministic fallback derives `STATED-nnn`/`SREG-nnn` scenarios from the PR description's behaviour statements (merged restatements, injected/meta lines skipped), each tagged `[STATED: PR description]` with "verify" expectations; the gate checks that generated prompts cover the stated requirements per scenario block (stemmed keyword overlap plus each requirement's distinctive terms; one scenario may be the primary cover of at most 2 requirements; <60% covered → fallback, gaps → warnings naming the requirement and best-matching scenario) and that `[STATED]` claims actually appear in the description. Not deterministic: semantics of requirements, enum values in prose, paraphrased duplicates with disjoint vocabulary.

### PRQA 04 · OpenCode Job Dispatcher
`Build Job Request` → `Submit Job to Worker` → `Job Accepted?` (201 accepted / 409 duplicate / 403 rejected by policy / other) → `Extract Job ID` → `Wait 10 s` → `Poll Job Status` → `Job Finished?` (succeeded / failed / **cancelled** → `Stop: Job Cancelled` / still running → `Poll Limit Reached?` → back to Wait) → failed → `Already Retried by n8n?` → `Request Manual Retry` → `Mark n8n Retry` → Wait … → `Attach Job Result`.
- The worker creates an isolated per-job workspace (`/data/workspaces/<job_id>`, marker + pinned checkout plan) when it starts a job; cancelled jobs (label removed / PR closed / superseded) end here and are never reported.
- Rejections are **Stop and Error** nodes with the worker's reason code in the message (visible in the execution list).
- The worker executes synthetic jobs with the mock executor; live jobs would use `worker/prqa_worker/opencode_runner.py` (Docker sandbox, `--cap-drop ALL`, read-only, secrets via stdin) — never reachable in review-only mode.

### PRQA 05 · Result Validation & Report
`Validate Result Schema & Counts (worker)` → `Result Valid?` → `Result Valid ✓` / `Build INVALID_RESULT Placeholder (INCONCLUSIVE)` → `Select Result for Rendering` → `Render Report / Discord / GitHub Comment (worker)` → `Attach Report`. Schema: `schemas/qa-result.schema.json`.

### PRQA 06 · Discord Reporter
`Discord Input` → `Deliver Discord Report (worker /notifications/discord)` → `Attach Discord Status` → `Delivered?` → `Discord: delivered ✓` / `Discord: failed / skipped (result unchanged)` → `Return Pipeline Data`.
- The worker (`worker/prqa_worker/discord.py` + `server.py::notify_discord`) refuses jobs that are not `succeeded` (409 — accepted ≠ completed), re-validates the result (invalid or not matching the job → honest INCONCLUSIVE, never PASS), claims `notifications.discord` on the job (duplicate guard, `sending` claims expire after 15 min), sanitizes untrusted text (mass/user/role mentions, Markdown, secrets; `allowed_mentions: {parse: []}`), splits long reports within Discord's limits (≤ 6 messages), delivers with bounded retries (timeouts, 429 `Retry-After`, 5xx; 4xx fail fast) and records the per-message outcome on the job. A delivery failure returns HTTP 200 with `delivered: false`, so the pipeline records it instead of failing the stage, and the job/result are untouched.
- **Mock vs real** is decided by the worker: real only when `endpoints.discord_mode == 'real'` (`AUTOMATION_MODE=live` + `REAL_DISCORD_REPORTING_ENABLED=true`) **and** `DISCORD_WEBHOOK_URL` is set in the worker environment. `GET /config` → `discord.real_delivery_possible`. In Phase 1 only the mock sink is reachable; no n8n node posts to Discord any more (the error handler's alert is the one exception, unchanged).
- Report content: repo + PR, title + link, tested SHA, status (passed / passed with known issues / failed / inconclusive / blocked), counts, bugs with severity + evidence + reproduction, blockers, validation warnings, job id, n8n execution id, Actions run link, and whether the prompt came from a live model or the reference fallback.

### PRQA 07 · GitHub PR Commenter
`Real GitHub Reporting Enabled?` (IF: worker `endpoints.github_comment_mode == 'real'` **and** `GITHUB_TOKEN` set) → `Post PR Comment (REAL GitHub API)` / `Post to Mock GitHub Sink (dry-run)` → `Attach GitHub Comment Status` → `Record Notification Status (worker)` → `Return Pipeline Data`. In Phase 1 only the mock branch can execute.

### PRQA 08 · Error Handler
`Error Trigger` → `Sanitize Error` → `Log Error Event (worker /events)` → `Load Policy (worker /config)` → `Real Discord Alerts Enabled?` → real / mock alert → end.

## 6. The one review-only exception: `PROMPT_LLM_LIVE_IN_REVIEW_ONLY`

`compose/.env` → `PROMPT_LLM_LIVE_IN_REVIEW_ONLY=false` by default. When set to `true` **and the worker is restarted**, the worker hands n8n the real
provider for the prompt-builder LLM only (`endpoints.prompt_llm_api_mode: real`, the model proxy URL + `PROMPT_LLM_MODEL`; without `PRQA_MODEL_PROXY_PROMPT_TOKEN` workflow 03 sends nothing and falls back); `review_only` stays `true`,
GitHub/Discord/PR comments/OpenCode stay mock or blocked, the registry stays disabled, and `Policy.self_check()` refuses to start if any of that
is not the case. `/config` lists the exception under `policy.exceptions`. Purpose: an explicitly approved test that a workflow-generated prompt
(synthetic fixture data + the reference template) reaches the provider and is validated/finalized. Set it back to `false` afterwards.
